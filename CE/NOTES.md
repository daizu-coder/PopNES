# PopNES 技術メモ(SHARP Brain / Windows CE)

コードは AI(Claude)が書きました。製作者はプログラムを読めません。製作者がしたのは、AI への指示と、実機(PW-G5300)での確認です。

PopNES を作る中でわかったことのうち、実機で確かめたことと、このリポジトリのコードで裏付けが取れることだけをまとめています。Brain 向けにほかのエミュレータを移植するとき、作業を始める前に AI に読ませることを想定しています。

実機で確かめた機種は SHARP Brain PW-G5300 だけです。ほかの機種での動作は確かめていません。

各項目の最後の( )は、もとにした開発メモの記録です。開発メモでは、作業の区切りを「ラウンド」と呼んでいます。「v1.0.3 の1回目」などは、公開を始めてからの開発メモの節の名前です。開発メモはリポジトリに入れていません。( )の無い項目は、今のコードで確かめられることです。

v1.0.0 より前のフロントエンドは、コミット 8db28ad にまとめて入っています。コアのファイル(`nes_emu/`・`libretro/`)は変えていません。`git diff upstream/master -- nes_emu libretro` が空であることで確かめられます。

## 全体の作り

- PopNES は libretro のフロントエンドとして作っています。`libretro/libretro.cpp` と `nes_emu/*.cpp` をそのままコンパイルし、`CE/ce_main.c` が `retro_init()`・`retro_load_game()`・`retro_run()` を呼び、画面・音・入力・環境のコールバック(`retro_set_*` に渡すもの)を実装しています
- コアは C++ です。作り始める前に、`new`/`delete`・純粋仮想関数・グローバルなオブジェクトのコンストラクタを使う小さなプログラムを `arm-mingw32ce-g++` で `-static-libgcc -static-libstdc++` を付けてリンクし、使う DLL が `COREDLL.dll` だけになることを `objdump -p` で確かめました。`nes_emu/` は STL・例外・RTTI を使っていません(grep で確認)(開発メモのラウンド1、2026-08-14)
- 今の `AppMain.exe` も、使う DLL は `COREDLL.dll` だけです。`arm-mingw32ce-objdump -p AppMain.exe` で確かめられます(開発メモの「v1.0.4 の1回目」、2026-10-09)
- コアの `retro_get_system_info()` は `need_fullpath = false` を返し、`retro_load_game()` は `info->data`・`info->size` から ROM を読みます。最初はパスだけを渡していて(`game.data = NULL`)、どの ROM を選んでも `retro_load_game` が失敗しました。今は ROM を `_wfopen()` で開いてまるごとメモリに読み、`data`・`size` で渡しています(`ce_main.c` の `LoadRomPath()`)。コアは `retro_load_game()` の中で PRG・CHR を別のバッファに写すので、読んだバッファは呼び出しのすぐ後に解放しています(開発メモのラウンド2、2026-08-14)。直したあと、複数の ROM が起動して遊べることを実機で確かめました(開発メモのラウンド4、2026-08-14)
- コア(`nes_emu/`・`libretro/`)には `fopen()` の呼び出しがありません(grep で確認)。ROM・`.srm`・ステートは、どれもフロントエンドが `_wfopen()` で開きます(開発メモのラウンド62、2026-09-05)
- コアの `valid_extensions` は `"nes"` だけです。ファイル選択で出すのも `.nes` だけです(`ce_fileopen.c` の `IsRomExtension()`)。zlib はリンクしていないので、`.zip` は開けません
- ROM を読んだときのログは `geometry=240x224 fps=60.000 sample_rate=32000` でした(開発メモのラウンド4、2026-08-14)。フロントエンドは `quicknes_use_overscan_h`・`quicknes_use_overscan_v` の問い合わせに答えていないので、コアの変数は初期値の false のままで、幅と高さから 16 ずつ引かれます(`libretro.cpp` の `retro_get_system_av_info()`)

## ビルド

- `CE/Makefile` は `-march=armv5te -mno-unaligned-access -O3` を付けています。`-flto` は使っていません
- `CE/Makefile` は `-DNO_UNALIGNED_ACCESS` も付けています。付けていなかったときは、ROM を選んだ直後に Datatype Misalignment(0x80000002)の例外で落ちました(BER の記録)。例外の番地を `arm-mingw32ce-addr2line` で引くと、`nes_emu/Nes_Ppu_Impl.cpp` の `calc_sprite_max_scanlines<8>::func` の `ldr r2, [r4, lr]` でした。`nes_emu/blargg_common.h` の `unaligned_uint32_t` は、`NO_UNALIGNED_ACCESS` が定義されているときだけ `packed` になります。上流の `Makefile` も、いくつかのターゲットでこの定義を付けています。付けたあと、複数の ROM が落ちずに遊べることを実機で確かめました(開発メモのラウンド3とラウンド4、2026-08-14)
- メニューの文字のフォントは、`make`(Galmuri14)、`make CE_FONT=shinonome`(東雲16)、`make CE_FONT=galmuri11`(GalmuriMono11)で切り替えます(`CE/Makefile`)(開発メモの「メニューのフォントを Galmuri14 に」、2026-09-27)

## 画面

- GAPI(`gx.dll`)は使っていません。描画は GDI だけでしています(開発メモのラウンド32、2026-08-25)。GDI にしたあと、ゲーム画面の色と位置、表示の大きさの切り替え、設定画面を閉じたあとの画面の戻りを実機で確かめました。体感では少し遅くなりました(開発メモのラウンド33、2026-08-25)
- `GetSystemMetrics` で取った画面の大きさは 480×320 でした(実機のログ)(開発メモのラウンド33、2026-08-25)
- 画面と同じ大きさの RGB565 の DIB セクション(`CreateDIBSection`、`BI_BITFIELDS`、`biHeight` を負にして上から下の順)にアプリのコードで拡大して書き、`BitBlt` で等倍のまま画面へ送ります(`ce_display.c` の `CeDisplayBlitRGB565()`)
- 表示の大きさは、x1 は等倍、x1.5 は 3/2(240→360)、Wide は 7/4(240→420)、Full は画面の幅(480 のとき 2倍)です。x1 のほかは、画面の高さいっぱいに広げます(`ComputeGeometry()`)。2倍・3/2・7/4 のときは、2画素を32ビットで1回に書く経路(`s_scale2x`・`s_scale3over2`・`s_scale7over4`)を通ります。1回分を 2・6・14 画素(4・12・28 バイト)にしているので、書き込みの番地はいつも4の倍数です
- Full(2倍)の転送の時間を、実機のログ(`perf: blit`)で順に測りました(フレームスキップ 0)(開発メモのラウンド43〜ラウンド49、2026-08-26)
  - GAPI の版は平均 9ms、GDI にした直後の版は平均 31ms でした
  - 毎フレームの `GetDC()`・`ReleaseDC()` をやめて HDC を持ち続ける形(`GetCachedWndDC()`)にしても、31ms のままでした
  - 内訳を測ると、DIB セクションに書く部分が 27ms、`BitBlt` が 3ms でした。このときの書き込みは、1画素ずつ表を引いて元の位置を求めていました
  - 2倍のときだけ1画素を読んで2画素分を32ビットで書く経路にしたら、書き込みは約4ms、転送の合計は約8ms、`retro_run` の平均は 37ms から約14ms になりました。色と位置、表示の大きさの切り替えも実機で確かめました
- x1(等倍、`memcpy`)の転送は平均 3〜4ms でした(実機のログ)(開発メモのラウンド33、2026-08-25、ラウンド36、2026-08-26)
- x1.5 と Wide は、ラウンド53 より前は縦横比から求めた倍率(約1.425倍、約1.7125倍)でした。実機のログでの書き込みの時間は次のとおりです(開発メモのラウンド50〜ラウンド54、2026-08-26〜2026-08-27)
  - 1画素ずつ表を引く形では 19〜20ms でした。元の列ごとの繰り返しの数の表を引く形にしても、ほとんど変わらず、体感でも遅いままでした
  - 表を使わず 16.16 の固定小数点の足し算で元の位置を進める形にしたら、11〜13ms になりました。色と位置も実機で確かめました
  - 倍率を 3/2・7/4 に決めて上の32ビットの経路を通したら、書き込みは 2ms、転送の合計は x1.5 で 5ms、Wide で 6ms、`retro_run` の平均は 10〜12ms になりました
- 表示の大きさや元の画像の大きさが変わったときは、画面全体を一度 `PatBlt` で黒く塗ってから描きます(`CeDisplayBlitRGB565()`)
- GDI でウィンドウに直接描くので、ダイアログを閉じて見えた部分は描き直す必要があります。`ce_main.c` の `WndProc` の `WM_PAINT` で黒く塗り、ゲームを読んでいれば `CeDisplayForceRepaint()` で DIB セクションに残っている最後の画像を送り直します(開発メモのラウンド32、2026-08-25)

## 速さ

- フレームの速さを合わせる処理が無かったころは、BGM に「ブツブツ」と雑音が入り、体感ではゲームの速さにむらがありました。実機のログでは、`retro_run` の平均が約15ms で NTSC の1フレーム(16.67ms)より短く、`ring overrun` と `audio underrun` が 0.2〜1秒おきに交互に出ていました(開発メモのラウンド13、2026-08-14)
- `GetTickCount()` で1フレームの時間に合わせる処理を入れたら、ブツブツは出なくなりました。体感でも良好でした(開発メモのラウンド14とラウンド15、2026-08-14)
- 今のコードは、waveOut が開けているときは、`retro_run` の前に、リングにたまった音が 64ms(`CE_FRAME_PACING_HIGH_MS`)以下になるまで `Sleep(1)` で待ちます(最大120回)。開けていないときだけ `GetTickCount()` で合わせます(`ce_main.c` の `WinMain`)。音のリングが空になったときは、最後の音から最大256フレームかけて 0 まで下げ、戻るときは最初の128フレームで 0 から上げます(`ce_audio.c` の `CeAudioThreadProc`)。この2つを入れたあと、「プチプチ」という音が無くなったことを実機で確かめました(開発メモ、2026-09-05)
- フレームスキップ(Video Config の 0〜30)は、コアの `RETRO_ENVIRONMENT_GET_AUDIO_VIDEO_ENABLE` に答えて使います。映像のビットを落とすと、コアは `Nes_Emu::emulate_skip_frame()` を呼び、CPU と音はふつうに動かして画面だけ描きません(`libretro.cpp` の `retro_run()`)。コアは `RETRO_ENVIRONMENT_SET_AUDIO_BUFFER_STATUS_CALLBACK` を呼ばないので、`ce_main.c` の `g_audioBuffStatusCb` は NULL のままです(開発メモのラウンド29、2026-08-22)
  - 飛ばすのは、音のリングが 25% より少ないか、前のフレームの `retro_run` が1フレームの時間(1000 / 60 で 16ms)より長かったときだけです。設定した数だけ続けて飛ばしたら、次のフレームは描きます(`ce_video.c` の `CeVideoFrameSkipDecide()`)
  - 上限 0〜4 のとき、0 で前と変わらないこと、1 以上で画面だけが間引かれて操作と音は途切れないことを実機で確かめました(開発メモのラウンド30、2026-08-22)。上限を 30 に広げたのはラウンド31(2026-08-25)です。上限を 5 以上にしても、画面だけが間引かれ、操作と音は途切れないことを実機で確かめました(開発メモの「実機での確認」)
  - 32ビットの経路を入れる前の Full では、フレームスキップ 0 で `retro_run` の平均が 35〜36ms、1 で 19〜22ms、2 で 13〜14ms になり、2 では `frame pacing fell behind` のログが出なくなりました(実機のログ)(開発メモのラウンド36、2026-08-26)
- コアの音の設定は、`quicknes_audio_nonlinear` に `"linear"`、`quicknes_audio_samplerate` に `"32000"` と答えています(`ce_video.c` の `CeVideoEnvGetVariable()`)。サンプリング周波数を `"auto"` にすると、`RETRO_ENVIRONMENT_GET_TARGET_SAMPLE_RATE` に答えていないので、コアは 48000Hz を選びます(`libretro.cpp` の `resolve_samplerate_hint()`)
- x1.5 のログでは、`frame pacing fell behind` が90秒で2回出て、どちらも `CeSaveSram: saved 8192 bytes` の 60〜80ms 後でした。Wide のログでは、同じように `.srm` を書いても出ませんでした(開発メモのラウンド54、2026-08-27)

## 音

- waveOut は1チャンネル(`nChannels = 1`)で開き、コアの左右の音を平均して1つにしています(`ce_audio.c`)
- 出力の周波数は Sound Config で Native(コアと同じ 32000Hz)・8000・11025・22050・33000・44100Hz から選びます。既定は 44100Hz・16ビットです(`ce_audio.c`)。8ビット・8000Hz・33000Hz に切り替えられることを実機で確かめました(開発メモのラウンド13、2026-08-14)。Native(32000Hz)で音が鳴ることを実機で確かめました(開発メモの「実機での確認」)
- 音のバッファが `WHDR_DONE` になるのを待つところは、待つ時間に上限を付けています。上限が無かったころは、待ちから抜けられなくなると、そのあと `waveOutWrite()` が呼ばれなくなる作りでした。上限を付けたあとの実機のログでは、上限に達して先へ進む行(`WHDR_DONE timed out`)が出ていました(開発メモのラウンド8とラウンド9、2026-08-14)
- 8000Hz で音が途切れ途切れになりました。1つのバッファは 1024 サンプルなので、8000Hz では 128ms 分になり、そのころの待ちの上限(100ms)より長くなります。今は待ちの上限を、開いた周波数でのバッファ1つ分の時間の 1.5 倍(100ms より短くはしない)にしています(`ce_audio.c` の `OpenAudioDevice()`)。直したあと、途切れがよくなったことを実機で確かめました(開発メモのラウンド16、2026-08-14)
- 8000Hz で音割れがひどくなりました。32000Hz から 8000Hz に下げるとき、4サンプルのうち1つだけを残していました(開発メモのラウンド13、2026-08-14)。今は「高音質」(Smooth)のとき、出力の1サンプルに入る元のサンプルを平均しています(`CeAudioPushSamples()`)(開発メモのラウンド15、2026-08-14)。この直しが効いたことを実機で確かめました(開発メモのラウンド16、2026-08-14)
- 音のリングバッファの大きさを ms で選べる設定を入れたときは、体感で処理落ちが増えたので外しました(開発メモのラウンド17とラウンド18、2026-08-14)。今の設定は KB で選ぶ形(4 / 8 / 16 / 32 / 64 / 128 KB、中はフレーム数で 2048〜65536、既定は 16 KB)で、あとから入れ直したものです(`ce_audio.c` の `kBufferChoices`)。大きさを変えても音が鳴り続けることを実機で確かめました(開発メモのラウンド55とラウンド56、2026-08-28〜2026-08-29)
- 設定を変えて waveOut を閉じるときは、`waveOutReset()` を呼ばず、送ったバッファが `WHDR_DONE` になるのを最大 500ms 待ってから閉じます(`ce_audio.c` の `CeAudioStop()`)

## 入力

- キーは `GetAsyncKeyState` で毎フレーム読みます(`ce_input.c` の `CeInputPoll()`)
- 既定の割り当ては、十字キーが方向、Enter が A、Backspace が B、A が連射A、S が連射B、Tab がセレクト、M がスタートです(`ce_input.c` の `s_map`)
- 連射A・連射B(コアの X・Y)を押しても何も起きませんでした。コアは `quicknes_turbo_enable` が既定の `"none"` だと連射のボタンを入力に入れません(`libretro.cpp` の `update_input()`)。今は `"player 1"` と答え、`quicknes_turbo_pulse_width` には `"3"` と答えています(`ce_video.c` の `CeVideoEnvGetVariable()`)(開発メモのラウンド20、2026-08-15)。連射が効くことを実機で確かめました(開発メモのラウンド27、2026-08-15)
- 決定ボタンでステートロードすると、ゲームに戻ったときにスタートボタンが反応して、ポーズしてしまいました。今は、メニューを閉じてゲームに戻る直前と、ROM の切り替えで新しいプロセスがゲームを始める直前に `CeInputSuppressStartKey()` を呼び、スタートのキーが一度離されるまでスタートを押されていないことにしています(`ce_input.c`)(開発メモのラウンド19、2026-08-14)。ラウンド28 の実機の確認で、この処理を含むそれまでの機能が壊れていないことを確かめました(開発メモのラウンド28、2026-08-17)
- 斜め(右上など)の行は、1つのキーで2方向を押します。`CeInputPoll()` で全部をいったん 0 にしてから OR でまとめます。既定ではキーが割り当てられていません。2方向が同時に入ることを実機で確かめました(開発メモのラウンド28、2026-08-17)
- コアの L・R(パレットの切り替え)は、Input Config から外しました(開発メモのラウンド20、2026-08-15)。`CeInputPoll()` は今も既定のキー(Q・W)で読んでいます

## ダイアログ

- `/opt/cegcc/arm-mingw32ce/lib/libcoredll.a` には `SetMenu`・`GetMenu`・`Arc`・`Pie`・`Chord`・`SetStretchBltMode`・`TransparentBlt` の名前がありません(`CreateMenu`・`AppendMenuW`・`DrawMenuBar`・`StretchBlt`・`RoundRect`・`Polyline` はあります)。`arm-mingw32ce-nm` で確かめられます。アプリのコードは、メニューを `DialogBoxW` のダイアログにボタンを並べて作り(`ce_res.rc` の `IDD_MAINMENU`)、メニューのアイコンの円弧は `ce_bmpfont.c` の `DrawArcPoly()` で点をつないで描き、マスコットの絵は背景の色を合成した 24 ビットの BMP にしています(このメモを書くときに確かめました、2026-10-09)
- ボタンはどれも `BS_OWNERDRAW` で、文字は `AppMain.exe` に入れたビットマップフォントを `SetPixel` で描きます(`ce_bmpfont.c`)。キーで動かすボタンは、サブクラスにして `WM_GETDLGCODE` で `DLGC_WANTARROWS | DLGC_WANTALLKEYS` を返し、方向キー・決定・戻るをアプリのコードで扱っています(`MainMenuBtnCtrlProc`・`SoundCtrlProc`・`VideoCtrlProc`・`InputBtnCtrlProc` など)(開発メモのラウンド37、2026-08-26)。この形で、メインメニューのキー操作、日本語の表示、日英の切り替えを実機で確かめました(開発メモのラウンド38とラウンド39、2026-08-26)
- RC で `CHECKBOX ..., BS_OWNERDRAW` と書くと、`BS_CHECKBOX`(2)と `BS_OWNERDRAW`(0xB)の OR は 0xB なので、チェックボックスではなくなります(cegcc の `winuser.h` の値)。No Sprite Limit とデバッグログのチェックは、`BM_GETCHECK` を使わず、`ce_video.c` の `s_noSpriteLimit`・`s_debugLog` を正として描いています(開発メモのラウンド37、2026-08-26)。タッチと決定キーの両方で切り替わり、開き直しても残ることを実機で確かめました(開発メモのラウンド39、2026-08-26)
- 設定画面には「キャンセル」がありません。戻るボタン(`IDCANCEL`)は OK と同じく、設定を保存して閉じます(`ce_audio.c`・`ce_video.c`・`ce_input.c`)
- Input Config を 190×170 DLU(メインメニューは 210×140)にしていたとき、Input Config を閉じると、メインメニューの外に Input Config の OK ボタンが残りました。高さを 140 にしたら消えました(開発メモのラウンド27、2026-08-15)。そのあと斜めの行を足して 190×170 に戻したときは、メインメニューが 210×140 のままでも残りませんでした(開発メモのラウンド28、2026-08-17)。今の `ce_res.rc` では、メインメニューは 210×154、Input Config は 190×170 です
- ファイル選択のリストで A〜Z のボタンを押すと、選択が動きました。`ce_fileopen.c` の `FileListCtrlProc` で、空白以上の `WM_CHAR` を元のリストボックスに渡さずに捨てています。A〜Z で選択が動かないこと、上下・左右・決定・戻るが今までどおりであることを実機で確かめました(開発メモの「v1.0.3 の1回目」、2026-10-07、コミット bdcf812、タグ v1.0.3)
- ファイル選択の左右はページ送りです(開発メモのラウンド38〜ラウンド42、2026-08-26、ラウンド60、2026-09-05)
  - 最後のページの行が足りないときは、先頭の項目がリストのいちばん上に来ませんでした。空の行を足すようにしたら、いちばん上に来ました(実機)(開発メモのラウンド39)
  - 今は6行ずつ(`CE_FILELIST_PAGE_SIZE`)で、行の数を6の倍数まで空の行で埋め、いつもページの先頭に移ります(`FillFileList()`・`FileListCtrlProc()`)(開発メモのラウンド40)
  - `LB_SETCURSEL` を先に呼んでいたときは、選択が一度下にずれてから上に戻るのが見えました。`LB_SETTOPINDEX` を先に呼ぶ順にしたら、見えなくなりました(実機)(開発メモのラウンド41)
  - `WM_SETREDRAW` と `InvalidateRect` でリスト全体を描き直していたときは、文字が1字ずつ出るように見えました。やめたら直り、ずれも出ませんでした(実機)(開発メモのラウンド42)
  - 最後のページと最初のページの間で回るようにしました。実機で確かめました(開発メモのラウンド60)
- ファイル選択では、フォントに無い字を □(U+25A1)で描きます(`ce_bmpfont.c` の `CeBmpFontDrawTextBoxedW()`)(開発メモのラウンド55、2026-08-28)。フォントに無い字が □ で出ることを実機で確かめました(開発メモの「実機での確認」)
- メインメニューは、色の付いた角の丸いボタンとアイコン、マスコットの絵の形です。スクリーンショットも撮れます。文字がボタンに収まること、マスコットと背景の境目が見えないこと、撮った BMP の大きさと色を実機で確かめました(開発メモのラウンド64、2026-09-25)
- メインメニューのフォーカスの枠は 3px、塗りは #2F5FA8、押したときは #23477E です。実機で確かめました(開発メモの「v1.0.3 の1回目」、2026-10-07、コミット f40a135、タグ v1.0.3)
- UI の言語の既定は日本語です。Video Config で切り替えます(`ce_lang.c` の `CeLangInit()`)。設定ファイルが無いときに日本語で始まることを実機で確かめました(開発メモのラウンド37とラウンド39、2026-08-26)
- ステートセーブは、はい・いいえの2つのボタンで確かめてから書きます(開発メモのラウンド58、2026-08-29)。はいを押すと、同じダイアログの中で結果を出します(`ce_main.c` の `SaveConfirmDlgProc`)(開発メモのラウンド63、2026-09-07)

## ファイルと設定

- 設定は `AppMain.exe` と同じフォルダの `popnes.cfg` に書きます(`ce_config.c`)。このファイルが作られて読み書きされることを実機で確かめました(開発メモのラウンド58、2026-08-29)
- ファイル選択は、前に ROM を選んだフォルダから始まります。フォルダは UTF-8 にして、設定の `VideoLastDir` に書きます(`ce_fileopen.c` の `CeShowFileOpenDialog()`)(開発メモのラウンド64、2026-09-25)
- 日本語を含むフォルダの ROM を読み込んで遊べることを実機で確かめました(開発メモの「実機での確認」)
- カートリッジのセーブ(`.srm`)は、メニューを開いたとき、別の ROM を開くとき、ゲーム中の30秒ごと、終了のときに書きます(`ce_main.c`)(開発メモの「v1.0.4 の1回目」と「v1.0.4 の2回目」、2026-10-09、コミット c9f16ed、タグ v1.0.4)
  - 30秒ごとと終了のときは、中身が読み込んだとき、または前に書いたときと同じなら書きません(`CeSaveSramIfChanged()`)。`.srm` がまだ無いゲームでは、中身が変わるまで、どの時点でも書きません(`CeSaveSramCheckpoint()`)
  - コアがセーブの領域を返すのは、iNES のヘッダの電池のビット(`mapper & 0x02`)が立っているときだけで、大きさはいつも 0x2000 です(`libretro.cpp` の `retro_get_memory_data()`・`retro_get_memory_size()`)。ROM を読むと、コアは `Nes_Core::open()` の中の `reset(true, true)` でこの領域を 0xFF で埋めます。PopNES は、`.srm` が無いときに 0 で埋めることはしていません
  - MMC5 の拡張 RAM(1KB、`mappers/mapper005.hpp` の `exram`)と、Namco 163 のチップの中の RAM(`Nes_Namco_Apu` の `reg`)は、セーブの領域に入らないので、`.srm` にも入りません
  - `.srm` があるゲームと、無い状態から始めたゲームで、セーブして起動し直して続けられました。ROM を切り替えるときに保存され、新しいプロセスで `.srm` を読めました。メニューを開いてから終了すると、書くのは1回だけでした(v1.0.3 では2回)。試したゲームはどれも遊んでいる間にセーブの領域を書き換えるので、30秒ごとに毎回書いていました(実機)(開発メモの「v1.0.4 の2回目」、2026-10-09)
- ステートセーブは ROM ごとに1つ(`<ROM のパス>.state`)です(`ce_main.c` の `CeSaveState()`)
- スクリーンショットは、`AppMain.exe` のフォルダの `Screenshots` に `<ROM の名前>_NNN.bmp`(RGB565、`BI_BITFIELDS`)で書きます。画面に出ている大きさの画像を使います(`ce_main.c` の `CeSaveScreenshot()`)(開発メモのラウンド64、2026-09-25)

## ROM の切り替えと終わり方

- 同じプロセスのまま ROM を切り替えていたころは、切り替えたあと音が出なくなりました(開発メモのラウンド11、2026-08-14)。今は、ゲーム中に別の ROM を開くときは、`CreateProcessW` で `AppMain.exe` を `CREATE_SUSPENDED` で起動し、ROM のパスをコマンドラインにまるごと渡します(`ce_main.c` の `RestartProcess()`)。今のプロセスは `CeShutdown()` で `.srm` を書き、二重起動を防ぐミューテックスを閉じてから、新しいプロセスを `ResumeThread` で動かし、`ExitProcess()` で終わります。新しいプロセスを作れなかったときは、今のプロセスで読み込みます(`LoadRomFlow()`)。切り替えるたびに音が鳴ること、ログで6回の切り替えがどれもこの順に進んだことを実機で確かめました(開発メモのラウンド11とラウンド12、2026-08-14)
- 終了は `ce_main.c` の `CeShutdown()` から `ExitProcess()` を直接呼びます。音のスレッドを止めて、セーブを書いてから呼んでいます

## アイコン

- `CE/icon/popnes.ico` の 16×16・32×32(どちらも 32bpp)には AND マスクがありませんでした(大きさで確かめた)。マスクを足し、マスクのビットと透明な画素(alpha=0)が全画素で一致することを確かめてから、実機でアイコンを確かめました(開発メモの「v1.0.2 の1回目」と「v1.0.2 の2回目」、2026-10-02、コミット 616cd5a、タグ v1.0.2)

## デバッグの進め方

- アプリが例外で落ちたときは、[Brain Exception Reporter(BER)](https://github.com/Sgch/ber) で例外の番地とレジスタを記録しました。`CE/Makefile` に一時的に `-g` を足してビルドし直し(作られる命令は変わりません)、`arm-mingw32ce-addr2line` で番地をソースの行に直しました(開発メモのラウンド3、2026-08-14)
- デバッグログ(Video Config の「デバッグログを有効にする」)は既定で OFF です。`WinMain` で設定を読んでから有効にするので、それより前の行はログに出ません(`ce_main.c`)。ログは `AppMain.exe` のフォルダの `popnes_debug.log` で、`CeLog()` は1行ごとにファイルを開いて閉じます(`ce_log.c`)(開発メモのラウンド55とラウンド56、2026-08-28〜2026-08-29)
- ログの各行の頭には、最初の行からの時間を付けています。音の途切れとあふれは、始まりと終わりに1行ずつ、続いた時間と数を書きます(開発メモのラウンド13、2026-08-14)。時間の単位は「秒.ミリ秒s」です。前は「ms」と書いていたので、1000倍短く読めました。音の途切れの行の長さ(「after Nms」)と、行の頭の時間の差を比べて見つけました(開発メモのラウンド36、2026-08-26)
- ログを ON にすると、60フレームごとに `perf: retro_run avg=… max=… blit avg=… max=…` の行が出ます。転送の内訳(`perf: blit … (write …, bitblt …)`)と、音をリングに入れる時間(`perf: audio_push`)の行も出ます(`ce_main.c`・`ce_display.c`)(開発メモのラウンド46、2026-08-26、ラウンド57、2026-08-29)。上の「画面」の数字は、この行で比べたものです
